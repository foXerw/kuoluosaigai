# 服务端基准（2026-11-06）

**用途**：同机相对比较，不是公网容量承诺。硬件/Node 版本随每次输出打印。
延迟在客户端**收到帧的当下**记录（不是整批结束后回算），因此是逐条到达延迟。

命令：

```bash
npm run bench:server -- --clients 20 --messages 50 --joiners 8 --history 30 --history-cap 0
```

## 基线（history 响应不限制）

| 指标 | 值（两次运行） |
|---|---|
| 环境 | win32 x64 / 12 cores，Node v24.16.0 |
| 广播 50 条 × 20 接收者 | p50 **10.39 / 10.56ms**，p95 **11.66 / 12.02ms** |
| 8 个新客户端同时入房 | joined 约 15ms |
| 历史风暴（房内 10 个响应者 × 30 条历史） | 每个新客户端 **10 份**响应，合计 **254,240 bytes**（仅 history-res） |

解读：真正随规模放大的是历史风暴——每个入房者向全房广播 `history-req`，
每个有缓存的成员都回一份，流量 ≈ 入房人数 × 响应者数 × 历史条数。
P2P 合并只需要 ≥2 份佐证，超过 3 份基本是纯浪费。

## 优化后（history 扇出上限 3）

同一命令加 `--history-cap 3`（0 = 不限制）：

| 指标 | 基线 | cap=3 | 变化 |
|---|---|---|---|
| 每入房者收到的 history-res 份数 | 10.00 | **3.00** | **-70%** |
| 8 个新客户端历史流量合计 | 254,240 B | **75,432 B** | **-70%** |
| 广播 p50 / p95（两次运行） | 10.39–10.56 / 11.66–12.02ms | 10.10–10.26 / 11.37–11.58ms | 未触碰广播路径，属同机噪声 |

结论：历史扇出上限把「入房人数 × 响应者数 × 历史条数」的 O(N²) 流量压到
O(入房人数 × 3)，同时保留 P2P 合并所需的 ≥2 份交叉验证。
