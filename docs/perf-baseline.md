# 服务端基准（2026-11-06）

**用途**：同机相对比较，不是公网容量承诺。硬件/Node 版本随每次输出打印。

命令：

```bash
npm run bench:server -- --clients 20 --messages 50 --joiners 8 --history 30 --history-cap 0
```

## 基线（history 响应不限制）

| 指标 | 值 |
|---|---|
| 环境 | win32 x64 / 12 cores，Node v24.16.0 |
| 广播 50 条 × 20 接收者 | 总耗时 15.2ms；p50 **15.12ms**，p95 **15.44ms** |
| 8 个新客户端同时入房 | joined 15.3ms |
| 历史风暴（房内 10 个响应者 × 30 条历史） | 每个新客户端 **10 份**响应，合计 **258,360 bytes** |

解读：回环下广播延迟主要来自事件循环派发；真正随规模放大的是历史风暴——
每个入房者向全房广播 `history-req`，每个有缓存的成员都回一份，
流量 ≈ 入房人数 × 响应者数 × 历史条数。P2P 合并只需要 ≥2 份佐证，
超过 3 份基本是纯浪费。

## 优化后（history 扇出上限 3）

同一命令加 `--history-cap 3`：

| 指标 | 基线 | cap=3 | 变化 |
|---|---|---|---|
| 每入房者收到的 history-res 份数 | 10.00 | **3.00** | **-70%** |
| 8 个新客户端历史流量合计 | 258,360 B | **79,552 B** | **-69%** |
| joined 用时 | 15.3ms | 19.3ms（本次运行噪声） | — |
| 广播 p50 / p95 | 15.12 / 15.44ms | 26.06 / 26.37ms | 与本次改动无关（未触碰广播路径，属同机运行波动） |

结论：历史扇出上限把「入房人数 × 响应者数 × 历史条数」的 O(N²) 流量压到
O(入房人数 × 3)，同时保留 P2P 合并所需的 ≥2 份交叉验证。广播路径未改动，
两组数字差异应视为本机测量噪声，需在同一次机器状态下重复才能严格比较。
