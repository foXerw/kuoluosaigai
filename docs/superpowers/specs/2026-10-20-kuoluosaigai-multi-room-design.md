# 多聊天室（Multi-Room）设计

日期：2026-10-20 ｜ 前置：docs/superpowers/specs/2026-06-27-kuoluosaigai-chatroom-design.md（v1 单房间）

## 1. 背景与意图

v1 聊天室是单全局房间。本轮实现「开放多房间」：保留开机抽签仪式感（抽中哪个频道就落地哪个公共房），在此之上用户可以自由切换房间、新建房间、按 ID 加入别人的房间。致敬原作的匿名频道生态：私密度来自「房间不可被查询」——想进朋友的房间只能靠他转发房间 ID；输入任意 ID「碰运气」是玩法的一部分。

一个贯穿性的浪漫设定：**服务器不存一条聊天记录**。房间的全部记忆活在场的人的浏览器里，靠 P2P 互相请求历史重建。最后一人离开，这段共同记忆就真的消失了。

## 2. 目标 / 非目标 / 反目标

**目标**
- 多房间：新建、按 ID 加入、切换、维护自己的房间列表
- 房间 = 纯 ID，服务器除 ID 注册表外不存任何房间信息
- P2P 聊天记录重建（服务器只转发，不落盘消息）
- 性能护栏：房间人数上限、历史同步上限、浏览器内存上限（本轮只做护栏，深度性能优化与摸测后续单独进行）
- 站内规则入口：向用户解释房间生命周期与数据原理

**非目标**
- 房间搜索/目录/排行榜；房间改名/公告/头像等任何元数据
- 消息持久化（服务器或 localStorage 存消息内容）
- 登录、封禁、审核、消息防伪（接受伪造风险，见 §8）
- 端到端加密；移动端深度适配；非 WS 兜底传输

**反目标（做出来也算失败）**
- 服务器存储任何消息内容 → 违背「记忆活在浏览器里」的核心设定
- 浏览器缓存随逛的房间数无限增长 → 缓存爆炸
- 提供任何形式的房间列表 API（除按精确 ID 查在线数）→ 「不可查询」是房间的隐私屏障

## 3. 核心模型：房间 = 纯 ID

- 房间 ID：6 位小写字母数字 `[a-z0-9]{6}`，新建时由服务器随机发号（36⁶ ≈ 21.8 亿空间：肉眼碰运气几乎不可能命中，创建撞车概率可忽略，短到适合复制转发）。
- **创建即永存**：ID 一经发出永久有效，无人在线也可以再次进入，房间不可被删除（从自己列表移除只是本地行为）。
- 服务器对房间只认识两件事：① 注册表——所有曾发号过的 ID（唯一落盘数据）；② 在线表——当前哪些连接在哪些房间里（纯内存）。
- 四个公共房 = 开机抽签的四个频道，ID 固定（我的决定：取频道 prefix 小写）：`setsubun` / `nebula` / `magenta` / `amber`。它们永远存在于注册表，永远不可从列表删除。
- 输入一个不在注册表里的 ID → **拒绝加入**（「不存在的房间」），这是碰运气玩法的输赢来源；ID 不可用于占坑建房。

## 4. 服务器设计

### 4.1 数据结构与落盘

```
registry: Set<string>                 // 全量房间 ID（含四个公共房种子）
roomsFile: append-only 每行一个 ID     // 启动时读入 registry；create 时追加一行
rooms: Map<roomId, Map<connId, info>> // 在线表，纯内存
clients: Map<ws, {nick, roomId, times[], connId}>
```

- 落盘文件路径 `server/data/rooms.log`（`.gitignore` 掉 data/；目录不存在则创建；可用 `KUO_ROOMS_FILE` 环境变量覆盖，测试用）。
- 启动时：读文件 → 并入 registry → 幂等补入四个公共 ID。
- 消息内容、时间戳、在线状态一律不落盘。服务器重启 = 房间清空、ID 仍有效。

### 4.2 WS 协议帧

昵称机制不变（连接 query param `?nick=`，合法则沿用）。`joined`/`presence`/`message` 等房相关帧仅发给**同房连接**（v1 的全站广播取消）。新增/变更帧：

**客户端 → 服务器**

| 帧 | 含义 |
|---|---|
| `{type:'join', roomId}` | 加入/切换房间（服务器原子地离开旧房+进新房）。ID 不在注册表 → `join-error:unknown`；满员 → `join-error:full` |
| `{type:'create'}` | 请求发号建房（写入注册表并直接加入） |
| `{type:'message', text}` | 在当前房发言（截断 280，限速 10/min/连接，均沿用 v1） |
| `{type:'history-req'}` | 在当前房内广播历史请求（服务器转发给房内其他成员，携带请求者 connId） |
| `{type:'history-res', roomId, to, messages}` | 把自己的该房记录（≤200 条）回给请求者（服务器路由，不转发全员） |
| `{type:'counts', roomIds}` | 按**精确 ID 批量**查询在线人数（抽屉列表展示用；不提供任何搜索/列举能力） |

**服务器 → 客户端**

| 帧 | 含义 |
|---|---|
| `{type:'assign', nick}` | 不变 |
| `{type:'created', roomId}` | 建房回执 |
| `{type:'joined', roomId, online, selfId}` | 加入成功；`selfId` 供 history-res 的 `to` 引用 |
| `{type:'join-error', roomId, reason}` | `unknown` \| `full` |
| `{type:'presence', roomId, online, events}` | 当前房的进出事件与在线数（v1 全局 presence/join/leave 改为按房） |
| `{type:'message', id, ts, nick, badge, text}` | **新增 `id`（服务器发的短唯一号）与 `ts`**，用于 P2P 历史去重排序 |
| `{type:'history-req', from}` | 房内转发来的历史请求（`from` = 请求者 connId，即回包时的 `to`） |
| `{type:'history-res', roomId, from, messages}` | 路由给请求者的历史响应（服务器仅当**响应者与请求者当前同房**时投递；客户端合并前校验 `roomId === 当前房`，双保险防跨房污染） |
| `{type:'counts', counts}` | `{roomId: n}`（不存在的 ID 不出现，客户端显示 `--`） |
| `{type:'rate'}` / `{type:'error'}` | 不变 |

`history-res` 不占用发言限速额度（消息条数由服务器硬截断 ≤200），但协议帧有自己的三道护栏（防脚本把「碰运气」变成枚举扫描、防 create 灌盘）：

- **join 失败节流**：每连接 60s 内「加入不存在房间」失败 ≤10 次，超了直接回 `{type:'rate'}`。真人输几个 ID 毫无影响；`join-error:full`（房间存在但满员）不算失败、不计入。
- **create 限速**：每连接 60s 内 ≤5 次，超了回 `{type:'rate'}`。
- **counts 批量上限**：单次请求 >50 个 ID 时服务器截断为前 50 个，不报错。

### 4.3 消息唯一号

`id` 由服务器在转发时生成：`<roomId 无关的全局自增> 的 base36` 或 nanoid 均可，只要求房内唯一 + 可比较无意义（排序靠 `ts`）。

## 5. 客户端设计（Vue 3）

### 5.1 状态与存储

- **我的房间列表**：`localStorage kuoluosaigai:rooms`，仅存 ID 数组（无消息内容）。四个公共房常驻置顶且不可删。加入成功/建房后自动入列。
- **消息缓存**：纯内存 `Map<roomId, Message[]>`。**每房上限 500 条（丢最旧）；全局 LRU 最多 20 个房间**，超出淘汰整房缓存。不写任何持久化存储。
- 昵称身份 = 现有 sessionStorage ANON-XXXX，跨房通用（一人一格，到哪都是同一个匿名号）。

### 5.2 P2P 历史重建

1. 收到 `joined` 且 `online > 1` → 发 `history-req`。
2. 收集响应窗口 **2s**（我的决定）；收到 `history-res` 先校验 `roomId === 当前房`，不符直接丢弃（防秒切房间的跨房污染）。到点合并：
   - ≥2 个响应者：只采纳 **≥2 个响应者都含有**的消息 id（同 id 内容不一致 = 篡改，丢弃）；
   - 恰好 1 个响应者：全盘采纳（单人可比性为零，接受，见 §8）；
   - 合并进本地缓存，按 id 去重、`ts` 排序。
3. 收到别人的 `history-req`：若本地有该房缓存 → 取最近 200 条回 `history-res`；没有就不回。
4. 重连回到房间同样触发上述流程（与首次进入无异）。

### 5.3 useChat 改造方向

`useChat(url)` 从「单房间会话」升级为「连接 + 当前房间」：暴露 `messages`（当前房视图，从缓存 Map 映射）、`online`、`join(roomId)`、`create()`、`rooms` 列表管理、`counts`。断线重连后自动重进当前房（延续 v1 的退避重连逻辑）。

## 6. UI（沿用终端风，摆放为我的决定）

- **顶栏**（改造 ChatRoom `chat__top`）：`● ROOM setsubun`（当前房间指示，公共房显示频道名+频道色，私房显示 ID+默认绿）｜ `[ROOMS ▤]` 抽屉开关 ｜ `[RULES ?]` 规则入口 ｜ `N online · status` ｜ `✕`。
- **右侧抽屉「我的房间」**（覆盖在消息流上的终端面板，Esc 优先关抽屉再关房间）：
  - `PUBLIC` 区：四个公共房，名称+色点+在线数，点击即切换，不可删；
  - `MY ROOMS` 区：自己加入/创建的 ID，行内显示在线数、`⧉` 复制 ID、`✕` 从列表移除（仅本地）；
  - 底部：`> join by id ____ ⏎` 输入加入（拒绝未知 ID）＋ `[+ NEW]` 建房（成功后自动入列并选中，弹终端风提示供复制/转发）。
  - 抽屉打开时发一次 `counts` 批量刷新在线数。
- **规则 Modal**：终端风全屏浮层（复用 v1 Modal 样式基调），中英混排，内容大纲：
  - 房间就是一个 6 位 ID；创建后永久存在，无法删除、无法改名；
  - 服务器不知道任何房间名册，不提供搜索——你知道 ID 才能进来；
  - 聊天记录不经过服务器存储：记忆只存在于当前在场者的浏览器里，会向新成员同步；最后一人离开，记录即消失；
  - 进入未知 ID 会被拒绝（碰运气需要运气）；
  - 护栏：单房 ≤100 人、历史同步 ≤200 条/份、本地缓存 20 房×500 条、发言 10 条/分钟、单条 ≤280 字、输错 ID ≤10 次/分钟、建房 ≤5 间/分钟（后两条是反脚本措施，把碰运气压回人手的速度）；
  - 警告：历史记录来自在场成员互相转发，多人可交叉验证，但**没有绝对防伪**——把房间里的话当街头传闻。
- 主题色：进入公共房时沿用频道主色（CSS 变量 + ConfigProvider，现机制）；私房回退默认终端绿 `#39ff14`。
- 落地流程不变：抽签 → 进入聊天室 → join 抽中频道的公共房 ID。首页 RESHUFFLE 仍在进入前可换落地房。

## 7. 规格与限制（常量，本轮拍板，后续摸测再调）

| 项 | 值 | 位置 |
|---|---|---|
| 房间 ID | 6 位 `[a-z0-9]` | server |
| 房间最大人数 | 100（满员拒绝加入） | server |
| 历史响应上限 | 200 条/份（服务器硬截断） | server |
| 历史响应窗口 | 2000 ms | client |
| 客户端每房缓存上限 | 500 条（丢最旧） | client |
| 客户端房间缓存 LRU | 20 个房间 | client |

| 消息长度 | 280 字（不变） | server |

| create 限速 | ≤5 次/60s/连接 | server |
| counts 批量上限 | ≤50 个 ID/次（超出截断） | server |

## 8. 信任模型（明确接受，不实现缓解）

- 房间 ID 即门票：不可搜索 + 随机短码 + 失败节流（§4.2）= 事实上的访问控制。对人手它是屏障；对脚本，枚举扫描被节流压回人手速度——但注意这是减速带不是墙，高强度分布式探测不在本轮防御范围。
- 历史可被在场成员伪造：加入者通过 ≥2 响应者交叉验证规避大部分场景；**房内只有 1 人时无从对质，全盘接受**——原作频道里也全是骗子，这是玩法的一部分。
- 实时消息同样不可防伪（badge 客户端自报，v1 已如此）。

## 9. 错误与降级

- `join-error:unknown` → 抽屉内终端风报错 `NO SUCH ROOM`；`:full` → `ROOM FULL`；join/create 触发节流 `rate` → `SLOW DOWN`。
- 历史响应超时/为零 → 静默，只显示自己已有缓存（空房重进 = 空视图，符合预期）。
- WS 断开 → 沿用 v1 退避重连 + 错误透出；重连成功后自动重进当前房并再次请求历史。
- localStorage 不可用（隐私模式）→ 房间列表退化为内存态（公共房仍在）。
- 未配置 WS 且非同源服务 → 沿用 v1 离线降级画面。

## 11. 决策记录

**用户拍板**：保留抽签落地+可切换/新建；房间列表本地私有、公共四房常驻、其余不可查询；靠转发 ID 邀请 + 输 ID 碰运气；房间=纯 ID 无元数据；随机短码；输入不存在 ID 拒绝；P2P 历史重建（记忆随最后一人离场而亡）；多人交叉验证接受单人房伪造风险；房间永存不可删（注册表为唯一落盘）；护栏参数按本文档设定，摸测后续单独做；规则入口必须有；UI 摆放由本轮设计者决定；枚举防护采「失败节流」（unknown 失败 ≤10/分，full 不计）、create ≤5/分、counts 批量 ≤50（builder-check 提出、用户拍板采纳）。

**我的决定（可推翻）**：公共房 ID 用频道 prefix 小写；注册表落盘（否则重启即「删房」，违背永存原则）；历史响应窗口 2s；≥2 响应者才采纳、单响应者全盘采纳；私房默认终端绿、公共房沿用频道色；抽屉放右侧；`counts` 按精确 ID 批量查询不违反「不可查询」（存在性本身随 ID 永存而公开）；消息 `id` 由服务器生成；`history-res` 免限速但服务器截断 200；`history-res` 携带 `roomId` 且服务器同房才投递（builder-check 发现的跨房污染 bug 修复）。

## 12. 部署影响

部署模型不变（`npm install && npm run build && npm start` 单进程）。唯一新增：`server/data/` 目录需可写（首次自动建）；Docker/平台重启不丢注册表（文件在则 ID 永生）；若想「世界末日」（所有房间 ID 集体失效）就删 rooms.log——这条也写进规则页彩蛋。
